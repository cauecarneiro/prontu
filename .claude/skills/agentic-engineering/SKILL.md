# Agentic Engineering

Use this skill for engineering workflows where AI agents perform most implementation work and humans enforce quality and risk controls.

## When to Apply

Use this agentic engineering workflow for **any** of the following:

- Planning a new feature where an AI agent will perform most implementation.
- Decomposing a large task into agent-executable units.
- Deciding which model tier to use for a specific task.
- Reviewing code generated by an AI agent.
- Tracking cost and efficiency of agent-assisted development.

## Operating Principles

> Apply these principles at the start of every task or feature cycle.

1. **Define completion criteria before execution.**
   - ❌ Anti-pattern: "I'll know it's done when it looks right."
   - ✅ Pattern: Write a concrete eval or acceptance test first.

2. **Decompose work into agent-sized units.**
   - ❌ Anti-pattern: "Implement the entire auth system."
   - ✅ Pattern: "Add password validation with these 3 rules."

3. **Route model tiers by task complexity.**
   - ❌ Anti-pattern: Using Opus for boilerplate.
   - ✅ Pattern: Classify task → pick cheapest tier that can handle it.

4. **Measure with evals and regression checks.**
   - ❌ Anti-pattern: Ship without re-running existing tests.
   - ✅ Pattern: Run both capability eval and regression suite after each change.

## Eval-First Loop

> Every implementation begins with an eval, not with code.

For detailed examples, see [references/eval-first-guide.md](references/eval-first-guide.md).

### Checklist

- [ ] Define **capability eval**: what new behavior must pass?
- [ ] Define **regression eval**: what existing behavior must NOT break?
- [ ] Run baseline and record failure signatures.
- [ ] Execute implementation (minimum code to pass).
- [ ] Re-run all evals and compare deltas.

### Quick Example

| Phase | Action | Output |
|---|---|---|
| Capability eval | "Parser handles nested brackets" | Test: `parse("[[a]]")` → `Node(Node("a"))` |
| Regression eval | "Existing flat parsing still works" | Test: `parse("[a]")` → `Node("a")` |
| Baseline | Run both evals | Capability: ❌ / Regression: ✅ |
| Implementation | Add recursive descent for nested brackets | Code diff |
| Re-run | Run both evals | Capability: ✅ / Regression: ✅ |

## Task Decomposition

Apply the **15-minute unit rule** — each unit should be completable by an agent in ≈15 minutes.

For templates and more examples, see [references/decomposition-patterns.md](references/decomposition-patterns.md).

### Criteria for a Well-Decomposed Unit

| Criteria | Question to Ask |
|---|---|
| Independently verifiable | Can I write a test/eval for just this unit? |
| Single dominant risk | Is there only one thing likely to go wrong? |
| Clear done condition | Can I state "done when X passes" unambiguously? |
| Minimal coupling | Can this unit be completed without knowing the internals of other units? |

### Decomposition Template

```
Parent task: [high-level feature]
├── Unit 1: [verb] [noun] — done when [eval]
├── Unit 2: [verb] [noun] — done when [eval]
└── Unit 3: [verb] [noun] — done when [eval]
```

### Example

```
Parent task: Add user authentication
├── Unit 1: Validate email format — done when regex test suite passes
├── Unit 2: Hash password with bcrypt — done when round-trip test passes
├── Unit 3: Create /login endpoint — done when integration test returns JWT
└── Unit 4: Add rate limiting — done when 429 is returned after 5 attempts
```

## Model Routing

Route tasks to the **cheapest model tier** that can reliably complete them.

For the full decision matrix, see [references/model-routing-matrix.md](references/model-routing-matrix.md).

### Decision Matrix

| Complexity Signal | Tier | Examples |
|---|---|---|
| Single-file, narrow scope, well-defined output | **Haiku** | Classification, boilerplate transforms, narrow edits, formatting |
| Multi-step logic, moderate scope, requires reasoning | **Sonnet** | Feature implementation, refactors, test writing, debugging |
| Cross-cutting concerns, ambiguous scope, high risk | **Opus** | Architecture design, root-cause analysis, multi-file invariants, security review |

### Escalation Rule

> Start at the lowest viable tier. Escalate **only** when the current tier fails
> with a **clear reasoning gap** (not just a wrong answer — a gap in capability).

### Quick Decision Flow

1. Is the task a simple transform or classification? → **Haiku**
2. Does the task require multi-step reasoning within a single domain? → **Sonnet**
3. Does the task span multiple files/systems or require architectural judgment? → **Opus**

## Session Strategy

| Situation | Action |
|---|---|
| Tasks share context (e.g., same module, same bug) | **Continue** session |
| Major phase transition (e.g., design → implementation) | **New** session |
| Milestone completed (feature done, PR ready) | **Compact** context, then continue or close |
| Context window > 60% utilized | Consider compacting or starting fresh |
| Active debugging in progress | **Never** compact — maintain full trace |

## Review Focus for AI-Generated Code

> Prioritize review effort on areas where AI models are weakest.

For the complete checklist, see [references/review-checklist.md](references/review-checklist.md).

### Review Checklist (by severity)

- [ ] 🔴 **Security & auth**: Are credentials, tokens, or permissions handled correctly?
- [ ] 🔴 **Error boundaries**: Are all failure paths handled? Are errors propagated or swallowed?
- [ ] 🟡 **Invariants & edge cases**: Are boundary conditions covered? Are assumptions documented?
- [ ] 🟡 **Hidden coupling**: Does this change affect other modules in non-obvious ways?
- [ ] 🟡 **Rollout risk**: Can this be safely deployed incrementally?
- [ ] 🟢 **Test coverage**: Are the new code paths covered by evals/tests?

> ⚠️ Do NOT waste review cycles on style-only disagreements when automated format/lint already enforce style.

## Cost Discipline

Track metrics per task to maintain cost awareness and identify inefficiencies.

### Tracking Template

| Field | Value |
|---|---|
| Task | _description_ |
| Model Tier | Haiku / Sonnet / Opus |
| Token Estimate | _input + output_ |
| Retries | _count_ |
| Wall-clock Time | _minutes_ |
| Result | ✅ Success / ❌ Failure |
| Escalation? | Yes (reason) / No |

### Rules

1. **Escalate model tier** only when the lower tier fails with a clear reasoning gap.
2. **Log retries** — more than 2 retries at the same tier signals a tier mismatch.
3. **Compare across tasks** — track cost per feature to identify optimization opportunities.

## Anti-Patterns

Avoid these common mistakes in agentic engineering:

| Anti-Pattern | Why It Fails | Fix |
|---|---|---|
| "Just use Opus for everything" | Wastes budget, no cost signal | Start with Haiku, escalate on reasoning gaps |
| Skipping evals | No way to measure progress or detect regressions | Always define capability + regression eval first |
| Mega-tasks ("build the whole feature") | Agent loses coherence in long context | Decompose into 15-min units |
| Compacting during debugging | Loses critical trace information | Only compact after milestone completion |
| Reviewing style instead of logic | Wasted human effort on automatable checks | Trust linters, focus on invariants and security |
