# iOS Code Quality Hook System (Plankton Pattern)

Integration reference for adopting write-time code quality enforcement (inspired by the Plankton architecture) specifically tailored for **iOS AI-Driven Development**.

By delegating formatting and linting to hooks (`swiftformat` and `swiftlint`), the AI agent does not waste tokens generating perfectly styled Swift code; the tooling corrects it silently behind the scenes.

## When to Activate

- Defining `.claude` or `mcp` server hooks for an iOS Vibe-Coding environment
- You want automatic formatting and linting on every Swift file edit
- You want the agent to automatically fix `swiftlint` warnings it introduces
- Resolving debates about spacing, indenting, or line length

## How It Works

### Three-Phase Architecture for Swift

Every time Claude Code edits or writes a `.swift` file, a `PostToolUse` hook executes this pipeline:

```
Phase 1: Auto-Format (Silent)
├─ Runs `swiftformat --quiet .`
├─ Automatically corrects indentation, bracket spacing, and modifier order
└─ No output sent to the main AI agent

Phase 2: Collect Lint Violations 
├─ Runs `swiftlint lint --quiet --reporter json`
├─ Collects Swift rule violations (e.g., Force Casts, Long Lines, Retain Cycles)
└─ Still no output to main agent

Phase 3: Delegate + Verify
├─ Spawns an internal Claude subprocess passing the SwiftLint JSON
├─ Model instructs to fix the specific lines (e.g. replacing `as!` with `as?`)
├─ Re-runs Phase 1+2 to verify fixes
└─ Exit 0 if clean, Exit 2 if unfixable violations remain (reported to main agent)
```

### What the Main Agent Sees

| Scenario | Agent sees | Hook exit |
|----------|-----------|-----------|
| No violations | Nothing | 0 |
| All fixed by subprocess | Nothing | 0 |
| Violations remain after subprocess | `[hook] N violation(s) remain in YourFile.swift` | 2 |

The main agent only sees issues the subprocess couldn't fix (like a mathematically impossible cyclomatic complexity). Most aesthetic and basic safety issues are resolved transparently.

## Setup Requirements

For this pattern to work on an iOS project:

1. **Install Tooling**
```bash
brew install swiftlint swiftformat
```

2. **Configure SwiftLint** (`.swiftlint.yml`)
Ensure rules match your Vibe-Coding aesthetics. Disable overly pedantic rules that confuse LLMs.
```yaml
analyzer_rules:
  - unused_import
disabled_rules:
  - trailing_whitespace # Handled by SwiftFormat
  - line_length         # Often triggers falsely on generated code
opt_in_rules:
  - empty_count
  - force_unwrapping
```

3. **Configure SwiftFormat** (`.swiftformat`)
```text
--indent 4
--allman false
--trimwhitespace always
--commas inline
```

## Anti-Pattern Defense

### Config Protection

AI agents (especially when frustrated) will often choose to modify `.swiftlint.yml` to disable a rule rather than actually fixing the code.

To prevent this, you should employ a **Config Guardian**:
- Define a `PreToolUse` hook that intercepts shell commands attempting to write to `.swiftlint.yml` or `.swiftformat`.
- Return an error: `[hook] You cannot modify code quality configs to bypass errors. Fix the Swift code instead.`

### Package Manager Enforcement

If your team mandates Swift Package Manager (SPM) over CocoaPods or Carthage:

- Block `pod install` or `carthage update` with a `PreToolUse` hook.
- Enforce usage of `xcodebuild -resolvePackageDependencies` or UI-driven SPM additions.

## Integrating with XcodeBuildMCP

If you are using `XcodeBuildMCP`, you can configure it to trigger `swiftlint` automatically as a Build Phase script, ensuring that code generated by the agent is linted immediately upon compilation, rather than waiting for a separate hook execution.
